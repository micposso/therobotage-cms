# Saved Spanish translations

English remains the source of truth. Spanish content is generated by the OpenAI Responses API and committed under `translations/es/`. The deployed site never calls OpenAI. English URLs stay unchanged; Spanish uses `/es` and the same content slugs.

## What is connected

- News Markdown, current robot profiles (including scores), live job Markdown, research articles, and Field Signals.
- Spanish content indexes and search; navigation, footer, cookie controls, and an accessible native language selector.
- Source hashes, model/version provenance, structure/link validation, and protection for manually reviewed translations.
- Spanish `html lang`, canonical URLs, language alternates, and sitemap entries for available translations.

`site-content/` contains reference briefs rather than the actual rendered pages. It is intentionally not published as translated page content. Learn pages use the same components in both languages: Robot Literacy, Live Robot Lab, the course index, every credential and curriculum, the partnership inquiry, and the access page. Other marketing pages and tools retain an English fallback notice. The external learning platform and English video/audio recordings are not translated by the page-copy pipeline. The Spanish homepage, research index, robot profiles, news, job board, and search render the exact same page components as English. The locale route is only a dispatcher; translated content is adapted to the existing data models. Shared homepage/research copy is stored in `src/lib/i18n/ui-es.json`.

The job database remains authoritative for both languages: Spanish overlays translated title, summary, and body while retaining live IDs, facets, salaries, application URLs, and expiry behavior. Spanish files are snapshots of the repository's job Markdown, with its publication/expiry filtering; a database-only edit requires syncing the Markdown and regenerating the translation. Spanish pages revalidate every 15 minutes, including expiry checks.

## Local workflow

From `frontend/`, configure `OPENAI_API_KEY` in `.env.local` (never `NEXT_PUBLIC_*`). The default model is pinned to `gpt-4.1-mini-2025-04-14`; override with `--model` or `OPENAI_TRANSLATION_MODEL`.

```powershell
# Inspect pending translations and source size. No API calls.
npm run translate:check

# Generate only new/changed translations. Uses at most three concurrent requests.
npm run translate -- run

# A bounded run for one collection or article.
npm run translate -- run --collection news --limit 1
npm run translate -- run --slug unitree-ipo-robot-platform

# Validate saved output, then build and deploy through the usual workflow.
npm run translate:test
npm run build
```

Supported collections: `news`, `robots-profiles`, `robots` (legacy), `jobs`, `scores`, `research`, `field-signals`. Legacy robot articles and unused score fixtures can be translated without advertising nonexistent public routes.

Research/Field Signals are currently authored in TypeScript. The command creates deterministic Markdown source snapshots in `translations/sources/` and a source-hash registry at `translations/catalog.json`; `prebuild` and `predev` refresh these without API calls. Do not edit generated snapshots or the catalog; edit `src/lib/articles.ts` or `src/lib/fieldSignals.ts`. Deleted research records are removed from the source snapshots. Orphaned Spanish files are ignored. If using `npx next dev` directly instead of the npm script, run `npm run translate -- sync` first after changing source content.

Commit source changes, translations, and source snapshots together. No API work happens in `next build`; pending translations fall back to English until generated and deployed. Failed API calls leave prior files intact and return a failing exit code. Rerunning skips successful files.

## Lower-cost archive jobs with Batch API

```powershell
npm run translate -- batch-prepare
npm run translate -- batch-submit
# The submit command prints the batch ID. Collection is a separate command:
npm run translate -- batch-collect --batch batch_REPLACE_WITH_ID
```

Keep `.cache/translations/` until collection finishes: it holds the request manifest associated with each batch. Batch preparation is free; submission makes paid API requests. Collection rejects results whose sources have changed and preserves reviewed translations. Pending batches can take up to 24 hours. Partial failures can be retried by preparing a fresh batch after collection.

## Reviewing and updating

Every generated file contains `translation.sourceHash`, `version`, `model`, `generatedAt`, and `reviewed: false`. Review factual meaning and terminology before production release. Automated checks protect structure and links; they do not establish linguistic accuracy.

Set `reviewed: true` after manually editing/reviewing a translation. The generator will not overwrite it. If its English source changes, the Spanish version stops being advertised until updated. To regenerate, deliberately change `reviewed` to `false`. To retain manual edits, update them against the new source and then set `sourceHash` to the SHA-256 of the current English source with CRLF normalized to LF. Changing the model alone does not retranslate existing valid files; bump the translation version for an intentional global regeneration.

## Language-choice UX

- The selector shows the actual page language as EN / ES beside the globe, with full language names for assistive technology.
- An explicit choice is saved as `tra-language` in local storage. No cookie or API request is needed.
- Returning to an unprefixed page restores Spanish when that page has a translation. An explicit `/es/...` URL wins over an English preference.
- Switching preserves the content slug, query, and fragment. “Read the original” uses `?lang=en` to stay in English without resetting the saved preference.
- Missing translations keep the English page and show a dismissible Spanish notice. The preference remains Spanish.
- If storage is blocked, switching still works for the current visit.

English pages live under `src/app/(english)/` (a URL-neutral route group). Spanish pages have their own root layout under `src/app/[locale]/`, so both languages produce correct static HTML without request-time locale detection. `src/components/SiteDocument.tsx` shares fonts, providers, and document chrome. Unknown language/content URLs return 404s rather than silently mapping to arbitrary English paths.

## Shared UI and layout regression checks

Edit the existing component in place for either locale. Never add a Spanish page layout or locale-specific replacement component. Use `useCopy()` in client components or `uiText(text, locale)` in server components. Add new UI source strings to `translations/ui-source.json`, then run `node scripts/translate-ui.mjs` to generate only missing translations. Existing saved UI translations are preserved.

The homepage uses unpinned navigation for both languages. The language switcher is in the shared header; the fixed desktop header appears on scroll. The homepage sidebar has no language switcher. The original mobile breakpoint remains 1024px.

After starting a production build, set `TRANSLATION_TEST_URL` to its origin and run `node --test scripts/translation-layout.test.mjs` to compare the rendered structures of both languages. Browser checks should also cover scroll visibility, mobile menu, storage preference, and Spanish job filters/search. English-only narration is omitted when no Spanish audio exists.

The Learn route registry is `src/lib/i18n/learn-routes.ts`; it derives credential URLs from the certification catalog. Labels, option text, and validation messages use saved Spanish copy, while submitted field names and option values remain unchanged. The Learn disclosure underline is positioned independently of its label so hover cannot squeeze the text into multiple lines.
